# 测试说明 v0.1

给接手的人看：这个项目有哪些测试、怎么跑、新增一个测试要做什么、坏了怎么查。

## 1. 日常用到的命令

| 命令 | 做什么 | 大概耗时 |
|---|---|---|
| `pnpm test:fast` | 静态检查 + 纯逻辑测试（不含数据库、不含战斗基准） | 约 4 秒 |
| `pnpm test` | 全部测试，并行跑 | 约 13 秒（原来串行约 59 秒） |
| `pnpm test:db` | 只跑需要数据库的测试 | 约 10 秒 |
| `pnpm test:pg` | 数据库测试换成真 PostgreSQL 再跑一遍 | 约 7 秒 |
| `pnpm test --only skills,mail` | 只跑名字在列表里的 | 看选了哪些 |
| `pnpm --filter @choke/api exec tsx scripts/run-tests.ts --serial` | 一次只跑一个（怀疑测试互相干扰时用） | 约 60 秒 |

另外两个不属于"测试"、但常配合使用的检查：

- `pnpm run typecheck`：类型检查。
- `pnpm exec eslint apps/api/scripts apps/api/src packages/shared/src`：代码风格检查。

**建议的习惯**：改代码过程中用 `test:fast`；提交前跑 `pnpm test` 加类型检查加 eslint；大改动、合并或上线前再跑 `pnpm test:pg`。

## 2. 测试是怎么被找到的

入口是 `apps/api/scripts/run-tests.ts`。它**自动发现**测试，不需要在任何清单里登记：

- `apps/api/scripts/test-*.ts` 里，源码含 `setupTestDb(` 的 → 数据库测试。
- `test-battle.ts` → 战斗基准（最慢，最先开跑）。
- 其余 `test-*.ts` → 纯逻辑测试。
- 另有两项静态检查：`content-check`（内容目录校验）、`skill-docs`（技能总表文档是否过期）。

**新增测试 = 新建一个 `scripts/test-名字.ts`，什么都不用改。** 文件名去掉 `test-` 就是它的名字（`test-mail.ts` 叫 `mail`）。
文件头请写一段注释说明测的是什么（现有文件都是这样，方便别人看懂）。

`test-db.ts` 是建库工具，不是测试，已被排除。

## 3. 为什么能并行

- 每个数据库测试都用自己的临时库，互不相干；
- 各测试不读写同一个磁盘文件（`data/rankings.json` 没有任何测试碰它）；
- 没有测试占用固定端口（服务用 Fastify 的 `inject`，不监听端口）。

如果以后写的测试要占端口或写共用文件，请在文件里自己处理，或者让 `run-tests.ts` 对它串行。

## 4. 两处提速的做法

1. **战斗基准用多个线程**（`test-battle.ts`）：每个遭遇一个任务，分给最多 8 个 worker 线程；结果按遭遇名排好序合并，所以输出和基准文件跟单线程时逐字节相同。用环境变量 `BATTLE_WORKERS=1` 可退回单线程（排查问题时用）。耗时从约 17 秒降到约 5 秒。
2. **数据库模板**（`test-db.ts` 的 `ensureTemplate`）：迁移只跑一次，建出一个已迁移好的 PGlite 目录放在系统临时目录里（名字叫 `choke-pglite-template-<哈希>`），每个数据库测试复制一份来用。哈希由迁移文件内容加 PGlite 版本算出，所以**改了迁移会自动重建，不用手动清理**；旧模板会被自动删除。第一次或迁移变了之后会多花约 4 秒。

走真 PostgreSQL（`test:pg`）时不用模板，每个测试各建一个 `choke_test_*` 临时库，跑完删掉，不碰开发库。

## 6. 战斗基准（最容易让人疑惑的一项）

`test-battle.ts` 让一个固定策略的机器人打 `content/encounters` 里的每一场遭遇，一共 1632 局：

- 三套通用卡组（`lib/battle-bot.ts` 的 `DECKS`：normal / mid / strong），每套 30 个固定种子，共 1440 局；
- 6 支流派队（`lib/archetypes.ts` 的 `PROBES`：平刀、法爆、持续伤害、迅捷、连击、续航反伤），每队 2 个种子，共 192 局，约占 12%。流派队统一是 L 品质、60 级、3 命座，比的是玩法差别，不是卡的强度。

检查三件事：

1. **确定性**：同种子同操作打两遍，结果逐位相同；
2. **可重放**：服务端用 `replayBattle` 复算的结果与实打相同（服务端防作弊靠的就是它）；
3. **回归**：每局的回合数、步数、终局摘要，与 `scripts/fixtures/battle-golden.json` 一致。

**挂了怎么办**

- 你**有意**改了引擎数值、技能或战斗内容：跑 `pnpm --filter @choke/api exec tsx scripts/test-battle.ts --update` 重录基准，把更新后的 `battle-golden.json` 和改动一起提交，并在提交说明里写为什么变了。
- 你**没打算**改战斗结果：说明改动误伤了战斗，先查清楚，不要直接重录。
- "同种子打两遍结果不同"：引擎里混进了不走种子的随机（比如 `Math.random()`），或依赖了外部状态。
- "重放结果与实打不同"：服务端校验会误判玩家作弊，是严重问题。

输出里的"僵局"提示（拖满回合上限没分出胜负）只是数值现象，不算失败。

## 8. 常见问题

- **`pnpm` 往 stderr 输出，PowerShell 里显示成红色 NativeCommandError**：不代表失败，看最后一行"全部通过 / 失败 N 项"和退出码。
- **失败时输出在哪**：并行跑时每项的输出先攒着，失败的那几项会在最后打印末尾 60 行。想看完整输出就单独跑：`pnpm test --only 名字`，或直接 `pnpm --filter @choke/api exec tsx scripts/test-名字.ts`。
- **只有并行时失败、单独跑没事**：用 `--serial` 跑一遍确认；多半是两个测试抢了同一份资源，见第 3 节。
- **提示缺少 `DATABASE_URL`**：`test:pg` 需要 `.env` 里有 `DATABASE_URL`，并且 PostgreSQL 已启动（`./scripts/postgres.ps1 status`）。
- **改了迁移后第一次变慢**：正常，模板在重建，见第 4 节。
- **提交前要补的检查**：测试不包含类型检查和 eslint，要另外跑（第 1 节）。

## 9. 接手后可以继续做的

- 把类型检查和 eslint 也纳入 `run-tests.ts`（现在是分开的）。
- eslint 加缓存（`--cache`）。
- 经济模拟测试：模拟玩家的市场行为（挂单、买卖、过期），校验金币总量不失控（用户已提出，未做）。
