## 0. 加一场战斗的流程

1. 写敌人：`content/enemies/<敌人id>.json`（§2–§4）。
2. 需要新的敌方支援，就在 `content/enemy-supports.json` 里加一项（§5）。
3. 写遭遇：`content/encounters/<遭遇id>.json`，指定敌人、支援、三星条件和简介（§6）。
4. 跑 `pnpm content:check`。字段写错、引用了不存在的 id，都会在这一步报出具体位置。
5. 跑 `pnpm test:battle --update`。新遭遇会进入回归基准，同时输出一张胜率表，用来粗调难度（§8）。
6. 本地进 `/battle?stage=<遭遇id>` 亲手打几局。
7. 提交时，把内容文件和 `apps/api/scripts/fixtures/battle-golden.json` 一起提交。

不需要改任何代码。如果发现非改代码不可（比如要一种新的条件或新的三星类型），见 §9。

## 1. 文件与 id

| 内容 | 位置 | id 从哪来 |
|---|---|---|
| 敌人 | `content/enemies/<id>.json`，一个文件一个敌人 | 文件名 |
| 遭遇 | `content/encounters/<id>.json`，一个文件一场战斗 | 文件名 |
| 敌方支援 | `content/enemy-supports.json`，一个对象装全部 | 对象的 key |

- id 只能用字母、数字和连字符，且必须以字母或数字开头（`/^[A-Za-z0-9][A-Za-z0-9-]*$/`）。建议全小写，例如 `ch1-elite-2`。
- 文件里**不写** `id` 字段，id 就是文件名。
- 两个目录下只能放 `.json`，不能有子目录。放了别的文件，服务端会拒绝启动，以免新内容被悄悄忽略。
- 遭遇 id 会出现在链接 `/battle?stage=<id>` 里，以后也会出现在地图节点和玩家记录里。**上线后不要改名**。要换内容就改文件内容；要下架就把 `listed` 设为 `false`。
- 敌人和遭遇是两层：同一个敌人可以出现在多场遭遇里，搭配不同的支援和三星条件，例如"普通版"和"带护卫的精英版"。
- 所有内容文件都计入 `contentVersion`。改任何一个字，版本号都会变；进行中的出征仍按开始时的版本重放。

## 2. 敌人

```jsonc
{
  "name": "断音重装卫队",          // 显示名
  "title": "高 T 多动精锐",        // 名字下面的小字
  "tier": "elite",                // normal / elite / boss
  "element": "thunder",           // 自身属性
  "weaknesses": ["fire", "ice"],  // 公开弱点：一直生效，一直显示，命中至少 +30%
  "hiddenWeaknesses": ["dark"],   // 可省略：隐藏弱点，一直生效，打中一次才显示
  "weaknessWindows": [            // 可省略：窗口弱点，条件成立的回合才露出，见 §2.1
    { "when": { "turnMod": [3, 0] }, "elements": ["thunder"] }
  ],
  "traits": [],                   // 特性，可省略
  "stats": { "hp": 52000, "atk": 820, "int": 760, "def": 2200 },
  "damageThreshold": 0,           // 可省略，见下表
  "enrageOnInterrupt": false,     // 可省略，见下表
  "ai": { "moves": { … }, "script": [ … ] }
}
```

| 字段 | 作用 |
|---|---|
| `tier` | 决定选关列表的排序（normal → elite → boss，同档按 HP），以及刺客打断的基础成功率：normal 65% / elite 55% / boss 45%。 |
| `element` / `weaknesses` | 属性取值：`metal` `wood` `earth` `ice` `fire` `thunder` `light` `dark` `physical`。 |
| `hiddenWeaknesses` / `weaknessWindows` | 另外两种弱点，见 §2.1。 |
| `traits` | 目前只有 `spirit`（灵体）：受到物理攻击 +20%。 |
| `stats.atk` / `stats.int` | 敌人物理招式按 `atk` 算伤害，其他属性的招式按 `int` 算（判断依据是招式的 `element` 是否为 `physical`，与 `kind` 无关）。 |
| `stats.def` | 减免我方伤害。 |
| `damageThreshold` | 单段伤害低于这个值时只算 100，用来做"硬壳"敌人，逼玩家堆单发。慎用，低练度卡组会完全打不动。 |
| `enrageOnInterrupt` | 打断它的蓄力时，默认让它进入 2 回合【脆弱】（受伤 +30%）；设为 `true` 则改为永久【狂暴】（ATK +40% / DEF −30%）。用来做"打断有代价"的 BOSS。 |

### 现有敌人的数值参考

| 敌人 | 档 | HP | ATK | INT | DEF | 每回合动作 |
|---|---|---:|---:|---:|---:|---|
| 谱面幽灵（教学） | normal | 3,600 | 160 | 180 | 400 | 1 |
| 谱面幽灵 | normal | 28,000 | 620 | 680 | 1,100 | 2–3 |
| 断音重装卫队 | elite | 52,000 | 820 | 760 | 2,200 | 3–4 |
| 失拍指挥·终曲 | boss | 120,000 | 1,080 | 1,180 | 2,800 | 3（+支援追击） |

新敌人先按档位套这张表的量级，再用 §8 的胜率表微调。

### 2.1 三种弱点

| | 公开弱点 `weaknesses` | 隐藏弱点 `hiddenWeaknesses` | 窗口弱点 `weaknessWindows` |
|---|---|---|---|
| 战斗里 | 一直生效 | 一直生效 | 条件成立的回合生效 |
| 界面上 | 一直显示 | 没打中过显示"？"；用该属性打中一次后显示属性 | 生效的回合显示"破绽"，回合结束收回 |
| 默认 | 必填（可以是空数组） | 空 | 空 |

没有公开弱点的敌人，平时就是没有弱点；实际生效的弱点 = 公开 ∪ 隐藏 ∪ 本回合露出的窗口。命中任何一种，伤害倍率至少 ×1.3（和原来的弱点规则相同）。

**窗口怎么写**

```jsonc
"weaknessWindows": [
  { "when": { "supportStacks": { "support": "enemy-sup-conductor-charge", "gte": 2 } }, "elements": ["ice"] }
]
```

- `when` 就是 §4.1 的那套条件，可以组合。
- **整回合固定**：窗口在每个玩家回合开始时算一次，和敌人意图是同一时刻。回合中途就算条件变了（比如打断了蓄力、血量掉过线），本回合的窗口也不变，下一回合开始时才重新算。这样玩家看到"破绽"就能放心规划这一回合。
- 同一个属性可以出现在多个窗口里（例如"第 3 回合"和"蓄力满"都露出冰）。

**隐藏弱点怎么算"打中"**

- 用该属性的技能、侧面支援攻击或迅捷抢攻命中敌人，就算打中；伤害被 `damageThreshold` 压成 100 也算。
- 按"这个属性在不在隐藏列表里"判断，**不是**看倍率。灵体吃物理 +20%、相克环顺时针 +25% 都不会误记。
- 战斗状态里的 `hiddenFound` 记录本场打中过的隐藏弱点，每个属性只记一次，同时发出一次 `weakness_found` 事件，界面弹"发现弱点"。
- 失败的战斗也记：打中了就是发现了。

**校验**

- 隐藏弱点不能和公开弱点重复，自己也不能重复。
- 窗口的属性不能和公开、隐藏弱点重复，同一个窗口里也不能重复。
- 窗口的 `elements` 不能为空。
- 窗口的 `when` 引用不存在的敌方支援，照样报错。

**设计提示**

- 隐藏弱点奖励"试出来"；窗口弱点奖励"留着 AP 和对应属性的卡，等破绽回合一口气打出去"。
- 窗口条件最有味道的是和敌人自己的节奏挂钩，比如"蓄力 ≥ 2 层时露出弱点"：同一回合敌人在攒大招，玩家要在"打断它"和"趁破绽猛攻"之间选。
- 界面上不显示窗口和隐藏弱点，但接口里的遭遇数据是完整的，想查随时查得到。这是有意的：游戏就是这样设计的，不做防抓包。

## 3. 招式 `ai.moves`

`moves` 是一张"招式表"，key 是招式 id（只在本敌人内部使用），脚本通过它引用招式。

```jsonc
"execute": {
  "kind": "heavy_phys",
  "label": "重装处决",               // 意图栏和日志显示的名字
  "element": "physical",
  "power": 1.55,                    // 伤害倍率
  "hits": 1,                        // 段数，可省略，默认 1
  "desc": "高额物理重击",            // 悬停意图时显示的说明
  "causesDown": false,              // 可省略
  "hardToInterrupt": false,         // 可省略
  "chargedUltimate": false,         // 可省略
  "status": "armor_break",          // 可省略
  "variants": [ … ]                 // 可省略，见 §3.2
}
```

### 3.1 `kind`：招式的行为

| kind | 实际效果 | 意图栏威胁 |
|---|---|---|
| `attack` | 对一名我方角色造成伤害（`power × hits`） | 低 |
| `magic` | 同上 | 中 |
| `heavy_phys` / `heavy_magic` | 同上，用于大招 | 高 |
| `debuff` | `power > 0`：造成伤害，并给全队挂上 `status`。`power = 0`：不造成伤害，只给全队挂 2 回合的 −20% 状态 | 低 |
| `buff` | 敌人攻击力 +20%，最多叠到 +60%。`power` 不起作用 | 低 |
| `add_support` | 在敌方支援栏召唤一个【魔物援军】（攻击型，ATK = 敌人 ATK × 75%，60% 概率追击）。栏位满 7 个时不生效。`power` 不起作用 | 低 |
| `break_support` | 拆掉玩家右侧最多 2 个非锁定支援。**不造成伤害**，`power` 不起作用 | 中 |

注意：

- 伤害类招式的目标：有嘲讽的角色优先；带 `causesDown` 的招式优先打坦克；否则随机挑一名，随机数走 `enemy` 流。
- 物理还是魔法看 `element`，不看 `kind`。`kind: "magic"` 配 `element: "physical"` 会按物理算，这样写只会让人困惑，别这么写。
- `add_support` 召唤的援军数值目前写死在引擎里。以后如果要"召唤指定支援"，再给招式加一个 `summon` 字段。

### 3.2 招式附加效果

| 字段 | 效果 |
|---|---|
| `causesDown` | 命中后判定 DOWN：被打中的卡倒地 3 回合。坦克的抵抗率为 45% + 防御档 × 15%，其他职业为防御档 × 12%。会让【无伤】星失败。 |
| `hardToInterrupt` | 难以打断：刺客盲抽时被抽中的权重只有 0.4（普通招式为 1），抽中后成功率 ×0.4。意图栏显示红色"难以打断"。 |
| `chargedUltimate` | 放完后清空敌方蓄力支援的层数。只和 `charge` 型支援配合使用。 |
| `status` | 命中后给全队挂上对应状态（伤害类招式：3 回合；`power = 0` 的 debuff：2 回合）。可用的 id 见 `packages/shared/src/battle/types.ts` 的 `STATUS_IDS`。常用：`burn` 燃烧、`fear` 恐惧、`armor_break` 破防、`weaken` 衰弱。 |

### 3.3 `variants`：随条件变化的招式

同一个招式在某些回合要变个样（多带 DOWN、变得难以打断、换描述），不用拆成两个招式，写成变体：

```jsonc
"variants": [
  { "when": { "turnMod": [2, 0] }, "causesDown": true, "desc": "高额物理重击（附带 DOWN 击倒威胁！）" },
  { "when": { "turnMod": [3, 0] }, "hardToInterrupt": true }
]
```

- 按顺序检查，**每条成立的变体都会叠加上去**，后面的覆盖前面的。上例在第 6 回合时两条都成立：既带 DOWN，又难以打断。
- 能覆盖的字段：`label` `desc` `element` `power` `hits` `causesDown` `hardToInterrupt` `chargedUltimate` `status`。不能改 `kind`。
- 改了效果，记得同时改 `desc`。意图是公开的，玩家靠 `desc` 做决定。

## 4. 行为脚本 `ai.script`

每回合开始时，引擎**从上到下**执行一遍脚本，命中的招式按顺序成为本回合的意图，并立刻公开给玩家。招式在敌方回合按这个顺序执行。

| 写法 | 含义 |
|---|---|
| `{ "always": "claw" }` | 每回合都用 |
| `{ "when": 条件, "use": "crush" }` | 条件成立时用 |
| `{ "otherwise": "beam" }` | 必须**紧跟**在一条 `when` 后面：前一条不成立时用这个 |

同一个招式可以在脚本里出现多次，表示一回合放两次。

### 4.1 条件

| 条件 | 写法 | 成立时机 |
|---|---|---|
| 回合取模 | `{ "turnMod": [3, 1] }` | 回合数 ÷ 3 余 1（第 1、4、7… 回合）。回合从 1 开始数 |
| 至少第几回合 | `{ "turnAtLeast": 5 }` | 第 5 回合及以后 |
| 支援层数 | `{ "supportStacks": { "support": "enemy-sup-x", "gte": 2 } }` | 该支援层数 ≥ 2。也可以写 `lte`，或者两个都写。支援不在场（被拆）时按 0 层算 |
| 血量比例 | `{ "hpBelow": 0.5 }` | 回合开始时敌人 HP 低于 50% |
| 全部成立 | `{ "all": [条件, 条件] }` | |
| 任一成立 | `{ "any": [条件, 条件] }` | |
| 取反 | `{ "not": 条件 }` | |

条件只读回合数、敌人血量和敌方支援，**不读玩家状态**。这是有意的：意图要在回合开始时就能确定并公开，玩家这回合做什么都不会让它临时改变。

### 4.2 常用写法

**交替出招**（单数回合 A，双数回合 B）：

```jsonc
{ "when": { "turnMod": [2, 1] }, "use": "a" },
{ "otherwise": "b" }
```

**蓄力满了放大招，否则放普通招**（终曲指挥）：

```jsonc
{ "when": { "supportStacks": { "support": "enemy-sup-conductor-charge", "gte": 2 } }, "use": "ult" },
{ "otherwise": "beam" }
```

蓄力支援在敌方回合末 +1 层（见 §5），所以写 `gte: 2` 的效果是："上回合末已经攒到 2 层，这回合就放"。玩家在意图栏看到大招以后，还有一整回合可以打断或拆支援。

**半血进入第二阶段**：

```jsonc
{ "when": { "hpBelow": 0.5 }, "use": "frenzy" },
{ "otherwise": "normal-attack" },
{ "when": { "all": [{ "hpBelow": 0.5 }, { "turnMod": [2, 0] }] }, "use": "big-hit" }
```

**开局几回合留手**：

```jsonc
{ "when": { "turnAtLeast": 3 }, "use": "crush" }
```

### 4.3 设计原则

- **意图公开，所以每个大威胁都要有应对办法。** 带 DOWN 的招式可以靠开防御档、嘲讽、打断来应对；难以打断的招式只能靠运气，就不要让它同时带 DOWN、又在同一回合和别的大招叠在一起。
- **一回合的动作数决定压迫感**：普通敌人 2–3 个，精英 3–4 个，BOSS 3–4 个外加支援追击。超过 5 个，意图栏会挤，玩家也难以思考。
- **节奏要能读出来**：用 `turnMod` 做出固定周期，玩家打两三回合就能摸清规律，三星挑战才有意义。不要用难以预测的条件组合去为难人。
- 脚本里没有随机挑招。需要"看起来随机"的效果，就用 `turnMod` 的不同周期叠出来（例如 2 和 3 的周期叠起来，6 回合才重复一次）。

## 5. 敌方支援 `enemy-supports.json`

敌方支援显示在敌方左侧的支援栏，最多 7 个。可以被我方技能拆掉。

```jsonc
"enemy-sup-vg-armor": {
  "name": "重装甲 II",
  "kind": "armor",
  "element": "metal",
  "defenseTier": 2,
  "roleText": "常驻防御 II 档 (−40%) · 可破防拆解"   // 支援格里的说明文字
}
```

| kind | 必填 | 效果 |
|---|---|---|
| `attack` | `atk`、`power`、`procRate` | 敌方回合末按 `procRate` 的概率追击一名随机角色，伤害 = `atk × power`（受我方防御影响） |
| `armor` | `defenseTier`（1–4） | 常驻防御档，减免我方对敌人造成的伤害：I/II/III/IV 档分别为 −20% / −40% / −70% / −90%。我方的破防每层降一档 |
| `thorns` | `atk` | 我方每段攻击命中后受到反伤 `atk`（按攻击卡的 INT 减免，最少 25），每次行动最多反 3 段 |
| `charge` | `maxStacks`；`stacks` 为初始层数 | 敌方回合末 +1 层，最多到 `maxStacks`。每层让敌人所有招式伤害 +18%。被我方打断时清零，敌人进入【脆弱】或【狂暴】（见 §2 `enrageOnInterrupt`）。配合 `supportStacks` 条件和 `chargedUltimate` 招式使用 |

- `locked: true`：表示这个支援不能被拆，只能用打断等方式处理。蓄力槽一般会锁上。
- 同一场遭遇里，一种 `kind` 最好只放一个。引擎找蓄力槽、荆棘时只认第一个。
- 支援 id 习惯写成 `enemy-sup-<敌人>-<作用>`。id 是全局的，不同遭遇可以共用同一个支援。

## 6. 遭遇

```jsonc
{
  "enemy": "conductor",
  "supports": ["enemy-sup-conductor-charge", "enemy-sup-conductor-armor", "enemy-sup-conductor-minion"],
  "stars": [
    { "type": "turnsAtMost", "value": 6 },
    { "type": "noDown" },
    { "type": "apSpentAtMost", "value": 18 }
  ],
  "summary": "终曲 BOSS：每回合 3–4 动……",  // 选关处的一句话介绍
  "intro": "……",                          // 可省略：开场日志，默认「讨伐开始：遭遇【敌人名】！」
  "listed": true                          // 可省略，默认 true：是否出现在自由讨伐列表
}
```

- `supports` 最多 7 个，不能重复，顺序就是支援栏里的显示顺序。
- `listed: false` 的遭遇不会出现在选关列表里，但仍然可以通过 id 进入。教学关、以后只在地图节点里出现的战斗，都这样设置。
- 内容里**必须**有 `tutorial-ghost` 这场遭遇（教程流程写死引用了它），并且至少要有一场 `listed` 的遭遇。

### 6.1 三星条件

每场遭遇正好 3 条，类型不能重复，顺序就是 ★1 ★2 ★3 的显示顺序。

| type | 参数 | 达成条件 | 显示 |
|---|---|---|---|
| `turnsAtMost` | `value` | 获胜时的回合数 ≤ value | ★ 速通 ≤ N 回合 |
| `noDown` | — | 全程没有人被 DOWN | ★ 无伤 无人被 DOWN |
| `apSpentAtMost` | `value` | 全场累计消耗的 AP ≤ value | ★ 高效 累计 AP ≤ N |

三星只看战斗结束时的状态，服务端复算以后得出的结论和客户端完全一致。

**怎么定数值**：

- 三星的目的是"同一场战斗再打一遍的理由"，不是第一次通关的门槛。
- 参考值：用中等卡组的平均回合数（§8 胜率表里的"平均回合"）× 0.6 左右作为速通线；AP 线定在"不浪费地打完"的水平。
- 现有四场：教学 3 回合 / 7 AP，幽灵 3 / 8，卫队 5 / 12，终曲 6 / 18。
- 遭遇的威胁不能 DOWN 人（没有带 `causesDown` 的招式）时，`noDown` 等于白送，最好换成别的条件。

## 7. 命名与文案

- 不复刻已有游戏的角色名、招式名、素材。名字从音游、谱面、乐理里取，和 osu! 玩家的语境呼应，例如"谱面幽灵""断音""失拍""终曲"。
- `desc` 要写清**效果**，而不只是氛围。玩家看意图做决定，"高额物理重击（附带 DOWN 击倒威胁！）"比"毁灭的一击"有用得多。
- 难以打断、DOWN、拆支援这类关键机制，用【】或明确的词点出来，和现有文案保持一致。

| 命令 | 做什么 | 什么时候跑 |
|---|---|---|
| `pnpm content:check` | 读取并校验 `content/`：字段、取值范围、交叉引用、文件清单 | 每次改内容 |

| `pnpm test` | 依次跑以上四个 | 提交前 |

### 8.1 改了内容以后

`test:battle` 会报"与基准不一致"，这是预期内的：内容变了，战斗结果就会变。

1. 确认报出差异的只有你改的那几场遭遇。如果别的遭遇也变了，说明改动影响到了共用的东西（共用的支援、引擎），先查清楚。
2. 跑 `pnpm test:battle --update` 重录基准。
3. 基准文件和内容一起提交，在提交说明里写清楚改了什么。

改引擎**不打算**改变数值（比如重构）时，`test:battle` 必须原样通过，不能用 `--update` 掩盖差异。

### 8.2 用胜率表调难度

`test:battle` 每次都会输出这张表：

```
│ ghost/normal          │ 23 │ 2  │ '6.9' │ '0.09' │
│ ghost/strong          │ 25 │ 0  │ '2.5' │ '2.84' │
│ vanguard/normal       │ 0  │ 25 │ '4.0' │ '—'    │
│ vanguard/strong       │ 25 │ 0  │ '6.1' │ '0.56' │
```

列依次是 胜 / 负 / 平均回合 / 平均星数。

- `normal` 卡组是中等练度（等级 18–30，命座 0–3），`strong` 卡组是满配（80 级、6 命）。
- 机器人很笨：不会看意图，也不会主动打断，只会"每张卡放第一个能放的技能，每 3 回合开一档防御"。所以这张表只能看**相对**难度和变化趋势，不代表真人的胜率。
- 粗略目标：普通敌人 normal 卡组大部分能赢；精英 normal 卡组打不过、strong 卡组稳赢；BOSS strong 卡组也会偶尔翻车。
- 平均星数接近 3，说明三星条件太松；strong 卡组都拿不到 1 颗，说明太紧。

## 9. 需要改代码的情况

| 想要 | 改哪里 |
|---|---|
| 新的 AI 条件（例如"我方有人倒地"） | `battle/content.ts` 的 `Condition` 和 `conditionSchema`、`battle/ai.ts` 的 `evalCondition`。如果条件引用了别的 id，还要在 `superRefine` 里加交叉检查 |
| 新的三星类型 | `battle/content.ts` 的 `starConditionSchema`，以及 `battle/stars.ts` 的 `starMet` / `describeStar` / `starProgress` |
| 新的招式行为 | `battle/types.ts` 的 `INTENT_KINDS`、`engine.ts` 的 `executeEnemyIntent`、`rules.ts` 的威胁等级 |
| 新的敌人特性 | `battle/types.ts` 的 `ENEMY_TRAITS`，再到对应的公式里读 `traits` |
| 新的支援类型 | `battle/types.ts` 的 `SUPPORT_KINDS`，以及 `engine.ts` 里处理敌方支援的几处 |

加完以后：

1. 在 `apps/api/scripts/test-content-errors.ts` 里补上对应的"改坏"用例。
2. 跑 `pnpm test`。
3. 如果新逻辑会影响已有遭遇的战斗结果，按 §8.1 处理。

**引擎里的随机一律走 `roll` / `random` / `pickOne`，并且指定流（`player` / `enemy`）**，不要用 `Math.random`。否则重放会对不上，`test:battle` 的确定性检查会直接报错。

## 10. 现阶段的限制（以后再做）

- 一场遭遇只有一个敌人，没有多体战。
- 掉落（`rewards`）还没接上，第 4 步随出征结算一起做。
- 隐藏弱点"已发现"只在单场战斗内有效；跨战斗的图鉴记录要等第 4 步的数据库，由服务端复算后写入。
- 现有 4 个敌人还没用上隐藏弱点和窗口弱点，等"敌人池 I"时一起加。
- `add_support` 召唤的援军数值写死在引擎里；`break_support` 固定拆 2 个支援。
- 招式挂给我方的状态，持续回合数和数值是固定的，还不能按招式配置。
- 脚本不能读玩家状态，这是有意的，见 §4.1。
